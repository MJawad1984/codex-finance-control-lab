# Control design

## Classification precedence

For each supplier/invoice/currency key:

1. More than one row on either side: AMBIGUOUS. Do not pair, net away, deduplicate or silently discard rows.
2. No source row: LEDGER_ONLY.
3. No ledger row: SOURCE_ONLY.
4. Exactly one row on each side and absolute source-less-ledger difference <= configured tolerance: MATCHED.
5. Otherwise: AMOUNT_MISMATCH.

Tolerance is only a grouping outcome rule; it does not write off money. Every difference remains visible. The default is zero in each configured currency. A change in tolerance/precision requires a new rule version and review; the manifest also hashes exact config bytes.

## Completeness and monetary controls

For each configured currency, each side's multiset of assigned record IDs must equal its input multiset. Counts and signed input amounts must equal grouped counts/amounts. This detects loss or double assignment; equal overall balances alone would not. Separate input totals and differences are reported even for empty populations. Equal populations do not establish source authenticity, tax eligibility, business validity or agreement with an independent general ledger balance.

## Architecture

`engine.py`: rule validation, CSV contract, classification, population and monetary controls. `__main__.py`: local file I/O, CLI, formula-safe CSV export and evidence manifest. There is no UI/provider-dependent business logic and no duplicated matching implementation.

## Worked reference, independently hand-calculated

USD source: 100 + 200 + 50 + 30 + 30 - 10 = **400.00**. USD ledger: 100 + 199.99 + 60 - 10 + 20 = **369.99**. Difference **30.01**, consisting of 50.00 source-only less 20.00 ledger-only plus 0.01 mismatch. Duplicate-key group 30 + 30 versus 60 is **AMBIGUOUS** despite zero difference. GBP 75 versus 75 is a separate matched group. These fixed reference values are not generated by the reconciliation engine. `scripts/check_example.py` checks the actual output against them.

## Evidence boundaries

The deterministic report and CSV contain no timestamps. The manifest records UTC execution time and interpreter version and therefore varies between runs. Its fingerprint combines exact input/rule hashes with the software version, not a signed code identity. Version control is required to identify exact code. SHA-256 establishes byte integrity only, not authenticity, authorization or a protected audit log. File outputs are editable by their owner.
